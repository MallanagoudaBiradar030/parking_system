Abstract

PARKEASE is a full-stack Parking Lot Database Management System developed as a DBMS mini project. The system automates the complete parking management workflow — from vehicle check-in and automatic slot allocation, to real-time occupancy tracking, dynamic fee calculation at checkout, and comprehensive revenue analytics.

The project demonstrates practical implementation of core DBMS concepts including relational schema design, referential integrity constraints, database views, triggers, stored procedures, aggregate queries, multi-table joins, subqueries, and indexing — all integrated within a production-quality Flask web application with a premium dark-themed UI.

Developed By: Mallanagouda S Biradar, Yashwanth R K, Varsha
Subject: Database Management Systems (DBMS) Mini Project

System Architecture

The application follows a classic 3-Tier Architecture pattern separating concerns between the presentation layer (HTML/CSS/JS), the application logic layer (Flask/Python), and the data persistence layer (MySQL Database).

Presentation Layer HTML5, CSS3, JavaScript, Chart.js, Jinja2 Templates
Application Layer Python Flask, Session Auth, Routing, Business Logic
Data Layer MySQL 8.0, InnoDB, Views, Triggers, Stored Procedures

Entity-Relationship Model

The database consists of 4 core entities connected through referential integrity constraints (foreign keys) with ON DELETE CASCADE behavior.

user
🔑 PK user_id INT AUTO_INCREMENT
UQ username VARCHAR(50)
password VARCHAR(256) — SHA-256 hash
full_name VARCHAR(100)
created_at TIMESTAMP
vehicle
🔑 PK vehicle_id INT AUTO_INCREMENT
UQ license_plate VARCHAR(20)
vehicle_type VARCHAR(20) — CHECK(Car|Bike|Truck)
owner_name VARCHAR(100)
owner_phone VARCHAR(15)
parking_slot
🔑 PK slot_id INT AUTO_INCREMENT
UQ slot_number VARCHAR(10)
slot_type VARCHAR(20) — CHECK(Car|Bike|Truck)
status VARCHAR(20) — CHECK(Available|Occupied)
parking_transaction
🔑 PK transaction_id INT AUTO_INCREMENT
🔗 FK vehicle_id → vehicle(vehicle_id)
🔗 FK slot_id → parking_slot(slot_id)
entry_time DATETIME
exit_time DATETIME (nullable)
fee DECIMAL(10,2)
status VARCHAR(20) — CHECK(Active|Completed)

Relationships

  • parking_transaction.vehicle_id → vehicle.vehicle_id (Many-to-One, ON DELETE CASCADE)
  • parking_transaction.slot_id → parking_slot.slot_id (Many-to-One, ON DELETE CASCADE)

Normalization Analysis

All tables in the PARKEASE schema are designed to satisfy up to Boyce-Codd Normal Form (BCNF), ensuring elimination of data redundancy, partial dependencies, and transitive dependencies.

First Normal Form (1NF)

  • All columns contain atomic (indivisible) values
  • Each row is uniquely identified by a primary key
  • No repeating groups or multi-valued attributes

Second Normal Form (2NF)

  • Already in 1NF
  • No partial dependencies (all PKs are single-column)
  • Every non-key attribute is fully functionally dependent on the PK

Third Normal Form (3NF)

  • Already in 2NF
  • No transitive dependencies exist
  • All non-key attributes depend only on the primary key

BCNF (Boyce-Codd NF)

  • Already in 3NF
  • Every determinant is a candidate key
  • No anomalies in any functional dependency

Database Views

Views provide virtual tables that simplify complex multi-table queries. They are used throughout the application to decouple the presentation layer from raw SQL complexity.

vw_currently_parked Joins parking_transaction, vehicle, and parking_slot tables using INNER JOINs to display all currently active parking sessions. Used by the Parked Roster and Vehicle Exit pages.
vw_slot_utilization Aggregates parking_slot data using GROUP BY and CASE expressions to calculate occupied vs. available counts and occupancy percentages per vehicle type. Powers the Dashboard and Entry form capacity indicators.
vw_monthly_revenue_summary Joins parking_transaction with vehicle and uses GROUP BY with DATE_FORMAT to compute monthly revenue totals categorized by vehicle type. Drives the Revenue Report analytics page.

Database Triggers

Triggers automate slot status management without requiring explicit application-layer updates, ensuring data consistency at the database engine level.

trg_after_transaction_insert

Event: AFTER INSERT on parking_transaction
Action: When a new Active transaction is created, automatically updates the associated parking_slot.status from Available → Occupied.

trg_after_transaction_update

Event: AFTER UPDATE on parking_transaction
Action: When a transaction status transitions from Active → Completed, automatically releases the slot by updating status back to Available.

Stored Procedures

Stored procedures encapsulate complex multi-step transactional logic at the database level, ensuring atomicity and consistency. They are called from Python using cursor.callproc().

CHECK-IN sp_park_vehicle

Handles the complete vehicle entry workflow atomically:

  • Upsert vehicle record (insert or update)
  • Prevent double parking (checks active transactions)
  • Auto-assign first available matching slot
  • Create active parking transaction
Signature: sp_park_vehicle(IN plate, IN type, IN name, IN phone, OUT slot_number, OUT transaction_id)
CHECK-OUT sp_check_out_vehicle

Handles the complete vehicle exit and billing workflow atomically:

  • Verify transaction exists and is active
  • Calculate parking duration (round up to nearest hour)
  • Apply tiered pricing (Bike: $2, Car: $5, Truck: $10 per hr)
  • Update transaction to Completed with fee and exit time
Signature: sp_check_out_vehicle(IN txn_id, OUT plate, OUT slot, OUT entry, OUT exit, OUT fee)
